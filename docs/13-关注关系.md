# 关注关系（M 扩展）

给「搭子」产品补一层社交图：关注感兴趣的人，方便回访对方主页、看其活动。
本期做**关注关系本体**（关注/取关 + 计数 + 列表 + 关注通知）与主页入口。

## 一、范围与口径

- **有向关注**：`follower 关注 followee`，单向关系，与"加好友"不同，无需对方同意。
- **幂等**：重复关注 = 已关注（不报错、不重复发通知）；取关一个没关注的人也不报错。
- **禁止自关注**：`follower == followee` 直接拒 `1001`。
- **计数**：主页展示 `followerCount`（粉丝数）/`followingCount`（关注数）。
- **通知**：关注成功给对方落一条 `USER_FOLLOWED` 站内通知（"XXX 关注了你"），点击跳**关注者主页**。
- **不做**：不加黑名单/拉黑、不做"互关"标识、不做关注动态流、**不影响匹配权重**（见第四节）。

## 二、数据模型

```sql
CREATE TABLE user_follow (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  follower_id BIGINT NOT NULL,   -- 关注者
  followee_id BIGINT NOT NULL,   -- 被关注者
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_follow (follower_id, followee_id),   -- 幂等防线
  KEY idx_followee (followee_id)                      -- 查粉丝用
);
```

`uk_follow` 保证同一对关系只有一行；`idx_followee` 优化"谁关注了我"。查"我关注了谁"走 `uk_follow` 的最左前缀 `follower_id`。

## 三、接口契约

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/user/{id}/follow` | 关注 id；幂等；不能关注自己（`1001`）；成功发通知 |
| `DELETE` | `/api/user/{id}/follow` | 取关 id；幂等 |
| `GET` | `/api/user/{id}/followers` | 粉丝列表（谁关注了 id），分页 |
| `GET` | `/api/user/{id}/following` | 关注列表（id 关注了谁），分页 |

`GET /api/user/{id}/profile` 的返回**新增**三个字段：
`followerCount` / `followingCount` / `following`（当前登录用户是否已关注目标；未登录、看自己时为 `false`）。

列表项 `UserBriefVO`：`userId` / `nickname` / `avatar` / `creditScore` / `banned` —— 与参与者列表同一口径，**不含手机号**。

## 四、与匹配算法的关系（刻意不做）

推荐算法里"标签重合 0.3 / 距离 / 信用分"权重是 **M7 实验的既定变量**。把"关注"接进权重会改变匹配结果分布，直接污染 M7 的对照数据。因此本期**只做社交图本体，不改匹配**；"关注的人的活动优先推荐"留到 M7 实验定稿后再评估。

## 六、联调结论

- 关注 → `code:0`，对方 `followerCount +1`、我的 `followingCount +1`；重复关注仍 `code:0`（幂等，不新增行、不重复发通知）。
- 取关 → `code:0`，计数 -1；对未关注者取关也 `code:0`。
- 关注自己 → `1001`「不能关注自己」。
- 关注不存在的人 → `1003`。
- 未带令牌 → `401`。
- 被关注方收到一条 `USER_FOLLOWED` 通知，`bizId` = 关注者 id。
- 数据已还原（测试账号的测试关注关系已清理）。
