# 成就勋章与个人主页

> 本文定"成就勋章 + 他人个人主页"的规则，是代码实现的唯一依据。M8 落地。
> 2026-10-14 TE 拍板开发；互评已砍（TE 判无用），本文不涉及。

## 一、要解决什么

组局产品的留存靠"下次还想来"。报名、发起、到场这些行为此前没有任何沉淀——用户做完就做完了，个人页只有两张列表。补两样东西把行为变成可积累的身份：**成就勋章**（行为里程碑，达成即通知）和**他人个人主页**（从参与者列表、私聊头像能看清对方是谁，主页徽章墙同时是勋章的展示位）。

## 二、徽章清单（首批 8 个，定稿）

| code | 名称 | 条件 | 触发方式 | 进度 |
|---|---|---|---|---|
| `FIRST_SIGNUP` | 初出茅庐 | 首次报名成功 | 即时（报名挂点） | 无 |
| `FIRST_HOST` | 初次组局 | 首次发布活动 | 即时（发布挂点） | 无 |
| `ATTENDED_3` | 靠谱伙伴 | 被组织者确认到场累计 3 次 | 即时（确认到场挂点） | n/3 |
| `JOIN_3` | 渐入佳境 | 完成 3 次活动 | 定时扫描 | n/3 |
| `JOIN_10` | 组局常客 | 完成 10 次活动 | 定时扫描 | n/10 |
| `HOST_3` | 小有名气 | 完成 3 次自己组织的活动 | 定时扫描 | n/3 |
| `HOST_10` | 金牌组局人 | 完成 10 次自己组织的活动 | 定时扫描 | n/10 |
| `FULL_HOUSE` | 座无虚席 | 组织的活动满员结束至少 1 次 | 定时扫描 | 0/1 |

几个口径：

- **"完成一次活动"的定义**：报名状态为 `SIGNED` 或 `ATTENDED`（不含 `CANCELED`、不含 `ABSENT`），且活动 `status = FINISHED`。缺席不计入——报名占了名额但人没到，算"完成一次流程"可以，算"参加"站不住。放鸽子另有信用分惩罚（`doConfirmAttend` 扣 10 分），不靠勋章叙事。
- **`HOST_*` 不设参与状态条件**：组织者自己不在报名表里，只要活动正常结束（FINISHED，非 CANCELLED）就算完成。
- **`FULL_HOUSE` 取结束时的计数**：`current_participants >= max_participants` 且 FINISHED。取消报名会走 `releaseSlot` 减计数，所以扫描时读到的就是最终值，不会把"曾满员又退了人"的活动算进来。
- **不做信用分类徽章**：信用分在本项目只有惩罚性出口（取消扣分、缺席扣分、举报扣分），加分渠道仅"被确认到场 +3"一种，"守信用"是默认义务而非成就，凑出来的徽章没有获得感。若日后信用体系长出奖励性规则，再在 `BadgeEnum` 末尾追加即可，枚举对扩展开放。
- **徽章定义放代码内枚举**（`BadgeEnum`），不建 badge 定义表：徽章是运营文案，改一次发一版；进库就要配管理端增删改，收益不抵复杂度。解锁记录才进库（`user_badge`）。

## 三、触发架构

两类触发，界线是"条件在操作当场就能判"还是"要等活动结束"：

- **即时类**（`FIRST_SIGNUP` / `FIRST_HOST` / `ATTENDED_3`）：挂在既有事务方法末尾，与同方法里的通知调用同一风格（事务内执行，失败随事务回滚）。三个挂点分别是 `SignupTxService.doSignup`、`ActivityServiceImpl.create`、`SignupTxService.doConfirmAttend`。
- **扫描类**（`JOIN_*` / `HOST_*` / `FULL_HOUSE`）：新 `BadgeScanJob`，`@Scheduled fixedDelay 60s`，扫"已结束但未评勋"的活动——`status = FINISHED AND badge_scanned = 0`——对组织者与全部有效报名者跑一遍阈值检查，然后条件更新置 `badge_scanned = 1`。**每场活动只扫一次**，与 `ReminderJob` 的 `reminded` 同一防重思路；不用 `updateById`，避免写回旧计数字段。

配套新增 `ActivityFinishJob`（同样 60s 一轮）：`end_time` 已到但状态还停在 `OPEN/FULL/ONGOING` 的活动（组织者忘了点"确认到场"）自动转 `FINISHED`。它同时是扫描类徽章的前置——没有它，忘记收尾的活动永远评不了勋。`doConfirmAttend` 已会把活动置 FINISHED，该 Job 只兜底。

解锁即发通知（类型 `BADGE_UNLOCKED`，复用通知域，`bizId` 留空——徽章没有可跳的详情页）。幂等靠 `user_badge` 的唯一索引 `(user_id, badge_code)`：并发场景下重复 insert 被数据库挡下，吞掉 `DuplicateKeyException` 视为"已解锁"，不重复发通知。

## 四、他人个人主页

入口两处：活动详情页的**组织者卡与已报名人头像**、消息页**私聊会话的头像**（整行仍是进入聊天，头像单可点）。自己点自己也进得去——相当于预览"别人眼中的我"。

`GET /api/user/{id}/profile` 返回：昵称、头像、简介、信用分、封禁态、已解锁徽章、组织/参加完成次数、最近 5 条活动（组织与参加合并，按开始时间倒序，标注角色）。

隐私口径：**手机号不返回**，其余字段本就是参与者列表已公开的信息（昵称/头像/信用分在 `participants` 接口里已有），主页只是换了个更完整的呈现。封禁用户主页可看，返回 `banned` 标志让前端置灰——封禁是状态不是消失，参与者列表里同样看得到。

## 五、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/badge/mine` | 我的徽章：全部 8 个，含未解锁（`unlocked=false` 时带 `progress/target`），按枚举序 |
| GET | `/api/user/{id}/profile` | 他人主页：公开资料 + 已解锁徽章 + 完成次数 + 最近活动 |

均为纯增量，不升契约版本。零新错误码（主页查不到人用 `1003`）。前端新增两页：`pages/badge/badge`（徽章墙，从"我的"菜单进）、`pages/user-profile/user-profile`（他人主页）。
