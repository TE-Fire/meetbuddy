# 接口契约

本文是前后端之间的唯一约定。契约定稿后 Flutter 侧按本文用 mock 开发，接口就绪时只替换数据源层。**契约变更必须改本文件并通知双方，不允许口头约定。**

## 一、通用约定

所有 HTTP 接口返回统一信封：

```json
{ "code": 0, "message": "ok", "data": {} }
```

`code` 为 0 表示成功，非 0 为业务错误，HTTP 状态码只表达传输层语义（鉴权失败仍返回 200 + `code=401`，便于前端统一处理）。分页参数统一为 `page`（从 1 开始）与 `size`，分页出参统一为 `{ "list": [], "total": 0, "page": 1, "size": 20 }`。

| code | 含义 | 前端处理 |
|---|---|---|
| 0 | 成功 | — |
| 401 | 未登录或令牌过期 | 尝试刷新，失败则跳登录页 |
| 403 | 无权限 | 提示并留在原页 |
| 1001 | 参数校验失败 | 展示 `message` |
| 1002 | 账号已被封禁 | 提示并退出登录态 |
| 1003 | 用户不存在 | 提示并留在原页 |
| 1004 | 资源不存在 | 刷新列表 |
| 1005 | 手机号已注册 | 提示并跳登录页 |
| 1006 | 手机号或密码错误 | 展示 `message`，不清空已填手机号 |
| 2001 | 活动已满 | 刷新活动状态 |
| 2002 | 重复报名 | 提示已报名 |
| 2003 | 信用分不足 | 提示当前分数与门槛 |
| 3001 | 验证码错误或过期 | 允许重新获取 |
| 3002 | 验证码发送过于频繁 | 倒计时，禁止重复点击 |
| 3101 | 不在该群聊中 | WebSocket `error` 帧 |
| 3103 | 消息帧格式不正确 | WebSocket `error` 帧，通常是客户端 bug |
| 3104 | 活动已取消，群聊转为只读 | 前端把输入框置灰 |
| 3105 | 不能给自己发消息 | 前端直接拦，不该发出来 |
| 5000 | 服务端异常 | 通用错误提示 |

### 错误码契约链（服务端实现约定）

上表的每个 code 在服务端都有唯一的枚举出处，不允许在业务代码里写裸数字。链条是：

```
IErrorCode（契约接口，只声明 getCode / getMessage 和快捷抛 ex()）
   ↑ implements
CommonErrorCode / ActivityErrorCode / SmsErrorCode …（按段位拆开的枚举）
   ↓ 消费方
BizException（只认 IErrorCode）/ BizAssert（isTrue / notNull / notBlank）
   ↓
Result.fail(IErrorCode)  →  GlobalExceptionHandler 统一翻译成响应体
```

**段位登记（新模块先在这张表里占段，再扩枚举）：**

| 段 | 归属 | 枚举 |
|---|---|---|
| 0 | 成功 | `CommonErrorCode.OK` |
| 401 / 403 | 鉴权（保留 HTTP 语义） | `CommonErrorCode` |
| 1xxx | 通用 / 用户 / 认证 | `CommonErrorCode` |
| 2xxx | 活动与报名 | `ActivityErrorCode` |
| 21xx | 搭子与匹配 | 预留 |
| 3xxx | 通知 / 短信 | `SmsErrorCode` |
| 31xx | 聊天 | `ChatErrorCode` |
| 4xxx | 管理端 | 预留（M6） |
| 5000 | 系统 | `CommonErrorCode` |

两条说明值得记下：

- **1xxx 里同时装着通用、用户、认证三类**，没有像校园市场那样按 1xxx / 4xxx 拆开。原因是这六个编号在 M1 就定稿并被 13 条验收用例锁死，重编号会让验收记录、前端约定、脚本断言同时失效，换来的只是枚举分得更细。21xx / 31xx 现在还是空的，等真有错误码时再立枚举。
- **401 / 403 保留 HTTP 语义**，没有并入 1xxx。前端 axios 拦截器见 401 直接跳登录页，不必再解析 body。

新增一个错误码的完整动作是：找到所属段位的枚举加一项 → 在本表登记 → 前端按需加分支。不需要改动 common 包的任何现有代码。

需鉴权的接口在 Header 携带 `Authorization: Bearer {accessToken}`。

### 配图上传 `/api/upload`

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/image` | multipart 上传单张图片，字段名 `file`，返回可直接用于 `<image src>` 的完整 URL |

发布/编辑活动时把返回的 URL 塞进 `images` 数组（上限 9 张，`@Size` 把关）；`coverUrl` 可以不传，后端自动取第一张兜底，feed 列表随即有封面可显示。

服务端落本地磁盘（`meetbuddy.upload.dir`，默认 `server/uploads/`，按天分目录、UUID 重命名、扩展名白名单、单张 5MB），经 `/uploads/**` 静态映射回读。该路径**刻意不挂 `/api/**`**：`<image>` 组件发不了 Authorization 头，活动图片本就是公开内容。

> ⚠ Windows 实测坑：`Path.toUri()` 对不带尾斜杠的目录**不会补 `/`**，而 Spring 按 URI 语义做相对解析——基址少了尾斜杠会把最后一段当文件名替换掉（`…/server/uploads` + `2026-10-14/x.png` → `…/server/2026-10-14/x.png`），文件明明在磁盘上却报 `NoResourceFoundException`。Boot 自带的 `classpath:/static/` 一类位置都带尾斜杠，照抄它就不会踩。

`lng`/`lat`/`radius` 三个参数要一起传才走 GEO 就近筛选；只传一部分时按代码的写法是**静默退化为**不带位置的普通分页列表，而不是报错——这是刻意留的容错，前端拿不到定位时不必改调用方式。`radius` 单位是公里，取值区间 **[0.5, 500]**：下界 0.5 是为了支持「附近 500 米」这类精搜，上界 500 覆盖「同城 + 周边城市」，再远已经不属于组局场景。超界返回 `1001`。搭子匹配的 `/api/buddy/match` 用同一区间。

## 五、搭子 `/api/buddy`

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `` | 发布搭子需求 |
| GET | `/match` | 匹配结果，参数 lng/lat/radius/limit |
| GET | `` | 我发布的需求 |
| PUT | `/{id}/close` | 关闭需求 |

`GET /match` 返回的每一项包含 `user`、`score`、`distance`、`commonTags`、`reason`。其中 `reason` 是给前端直接展示的一句话解释（如"距离 1.2km，都喜欢剧本杀"）——匹配算法如果只给一个分数，用户无法判断为什么要联系这个人，产品的说服力会大打折扣。

评分权重：距离 0.4、标签重合 0.3、时间匹配 0.2、信用分 0.1，信用分按 `credit_score / 100` 归一化后参与计算。每个分量的具体算式见 `01-技术决策与业务规则.md` 第七节，总分落在 `[0,1]`。

候选取自 Redis GEO：先按 `lng/lat/radius` 圈出半径内的需求，再对这几十条做加权排序。

## 六、聊天

WebSocket 端点 `/ws?token={accessToken}`，连接建立时校验令牌。客户端帧：

```json
{ "type": "chat", "groupId": 1, "content": "..." }
{ "type": "chat", "receiverId": 2, "content": "..." }
{ "type": "read", "msgId": 100 }
{ "type": "heartbeat" }
```

服务端帧：`chat`（新消息，本体在 `message` 字段）、`ack`（服务端**已落库**，带 `msgId`，客户端收到即可停止重发）、`offline`（重连时补发的离线消息，装在 `messages` 数组里，按时间正序）、`pong`，以及 `error`（带 `code` + `message`，码取自 31xx 段）。

心跳间隔 30 秒，服务端 **90 秒收不到任何帧**即断开——判据是"任何帧"，不只是显式的 `heartbeat`：有消息往来同样续期，没必要让客户端在连发消息时还额外补心跳。

**未读与离线补发的口径。** 单聊用 `message.read_status`，一条消息只有一个接收人，够用。群聊不行——一条群消息多人可见，一位 tinyint 表达不了"谁读到哪"，所以群聊改用 Redis 游标 `chat:read:{userId}:g{groupId}` 记每人各自读到哪条（游标没有时退回用 `chat_group_member.joined_at` 兜底，免得新人一进群被历史消息刷一脸未读）。重连时 `offline` 补发的就是这两部分之和，单群限量 50 条、总量上限 200 条，防止一个刷屏的群把补发配额吃光。

HTTP 侧只负责历史数据：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/chat/groups` | 我的群列表，带最后一条消息与未读数 |
| GET | `/api/chat/sessions` | 我的单聊会话列表：每个有过私聊的对方一项，带 `peerId`/`peerNickname`/`peerAvatar`、最后一条消息（`lastMessage`/`lastMessageAt`，`selfLast` 标记是否我发的）与未读数 `unread`，按最近消息倒序 |
| GET | `/api/chat/group/{id}/messages` | 群历史，参数 before/size |
| GET | `/api/chat/session/{userId}/messages` | 单聊历史 |
| GET | `/api/chat/unread` | 未读总数 |
| GET | `/api/chat/stats` | 投递计数：accepted、实时/最终到达率、离线积压、在线连接数 |

## 八、通知 `/api/notification`

> 规则见 `docs/05-通知与提醒.md`。通知 = 落库 +（接收方在线时）经 WebSocket 推一帧 `{ "type": "notify", "notification": {...} }`，与聊天帧复用同一条 WS 连接。未读与聊天未读**分开统计**。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/notification` | 我的通知分页，参数 page/size，按时间倒序 |
| GET | `/api/notification/unread` | 未读数 |
| POST | `/api/notification/{id}/read` | 标记单条已读 |
| POST | `/api/notification/read-all` | 全部已读，返回标记条数 |

事件类型：`SIGNUP_NEW`（有人报名我的活动 → 组织者）、`ACTIVITY_CANCELLED`（组织者取消活动 → 有效报名者）、`ACTIVITY_REMINDER`（开始前 N 分钟 → 组织者 + 报名者；N 由 `meetbuddy.notification.reminder-lead-minutes` 配置，默认 30，`ReminderJob` 每分钟扫一轮、靠 `activity.reminded` 防重）、`ACTIVITY_TAKEDOWN`（管理端下架活动 → 组织者，含原因）、`REPORT_HANDLED`（管理端处理举报 → 举报人，成立与否都回执）、`BADGE_UNLOCKED`（获得成就勋章 → 本人，`bizId` 为空、不可跳转）。错误码占 32xx 段（`NotificationErrorCode`）。

## 十、版本与变更

契约版本写在响应头 `X-Api-Version`。破坏性变更必须升版本并保留旧版至少一个迭代，避免 Flutter 侧正在开发的页面突然失效。

**2026-10-14**：新增 `GET /api/chat/sessions`（我的单聊会话列表），纯增量，不升版本。同时校正单聊已读口径——`markRead` 由“只标指定一条”改为“标到该条为止（含同一发件人更早的未读）”，与群聊游标“读到哪算到哪”对齐；旧行为下进房间只读最新一条会让之前连发的未读残留在列表里，新行为无字段增删、不构成破坏性变更。

**2026-10-14**：新增通知域 `/api/notification`（列表 / 未读 / 已读 / 全部已读）+ 活动开始前提醒（`ReminderJob` 定时）+ 两个事件通知（有人报名 → 组织者、活动取消 → 报名者）。新增 `notification` 表与 `activity.reminded` 列（migrate_m7）、WS `notify` 帧，均为增量，不升版本。规则见 `docs/05-通知与提醒.md`。

**2026-10-14**：通知域扩充两个管理侧类型——`ACTIVITY_TAKEDOWN`（管理端下架活动 → 组织者，含原因；`handleReport` 举报成立连坐下架同样触发）与 `REPORT_HANDLED`（管理端处理举报 → 举报人，成立与否都回执，附处理结果）。挂点在 `AdminServiceImpl.takedown` / `handleReport`，无新接口新字段，不升版本。

**2026-10-14**：新增成就勋章域 `GET /api/badge/mine` 与他人主页 `GET /api/user/{id}/profile`；通知域新增 `BADGE_UNLOCKED` 类型（徽章达成即时推送，不可跳转）；新增 `user_badge` 表与 `activity.badge_scanned` 列（migrate_m8）、`BadgeEnum` 代码内徽章定义（首批 8 枚）、两个定时任务（`ActivityFinishJob` 到点结活动、`BadgeScanJob` 结束评勋）。均为增量，不升版本。规则见 `docs/06-成就勋章与个人主页.md`。
