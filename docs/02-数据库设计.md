# 数据库设计

库名 `meetbuddy`，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。所有表都有 `id`（BIGINT 自增主键）、`created_at`、`updated_at`，下文不再重复列出这三个字段。

设计上有两个贯穿性的判断：**活动与搭子需求是两张独立的表**，不要合并；**消息用一张表承载单聊和群聊**，不要拆成两张。

活动是有明确时间地点、有人数上限、需要报名和截止的事务；搭子需求是一个没有终止条件、只求匹配的意向。强行合并会让双方都带上一半用不到的字段，最后变成一张充满 nullable 的宽表。消息表同理——单聊和群聊的差异只在"这条消息发给谁"，用一个 `group_id` 为空与否来区分就够，拆表反而让"未读数""历史记录"这类查询要 union 两次。

## 一、用户域

### `user` 用户

| 字段 | 类型 | 说明 |
|---|---|---|
| phone | varchar(11) | 唯一索引，登录账号 |
| password_hash | varchar(100) | BCrypt，可为空（纯验证码注册时） |
| nickname | varchar(32) | 昵称 |
| avatar | varchar(255) | 头像 URL |
| gender | tinyint | 0 未知 / 1 男 / 2 女 |
| bio | varchar(200) | 个人简介 |
| credit_score | int | 信用分，默认 100，区间 [0,100] |
| status | tinyint | 0 正常 / 1 封禁 |
| last_lng | decimal(10,7) | 最近一次上报的经度，LBS 匹配用 |
| last_lat | decimal(10,7) | 最近一次上报的纬度 |
| last_active_at | datetime | 最近活跃时间 |

`last_lng/last_lat` 存在表里、同时写一份到 Redis GEO。MySQL 里的这一份是持久化的底账，Redis 挂了可以用它重建索引——GEO 只当索引用，不当数据源。

### `user_tag` 用户兴趣标签

`user_id` + `tag_name`，联合唯一索引。标签用**字符串**而不是字典表：兴趣标签是开放集合（剧本杀、飞盘、探店、考研自习……），做成字典表每加一个兴趣就要改一次数据，收益为零。标签的规范性由前端的输入建议列表负责，不靠数据库约束。

### `favorite` 收藏

`user_id` + `activity_id`，联合唯一索引。

## 二、活动域

### `activity` 活动

| 字段 | 类型 | 说明 |
|---|---|---|
| organizer_id | bigint | 组织者 |
| title | varchar(64) | 标题 |
| description | varchar(2000) | 详情 |
| category | varchar(32) | 分类：剧本杀/运动/探店/拼车/其他 |
| cover_url | varchar(255) | 封面图 |
| lng / lat | decimal(10,7) | 活动地点坐标 |
| address | varchar(255) | 地点文字描述 |
| start_time / end_time | datetime | 起止时间 |
| max_participants | int | 人数上限 |
| current_participants | int | 当前报名数，冗余字段 |
| status | varchar(16) | OPEN/FULL/ONGOING/FINISHED/CANCELLED |
| credit_required | int | 参与所需最低信用分，默认 60 |
| group_id | bigint | 关联群聊，活动创建时生成 |

`current_participants` 是冗余字段，存在的理由是列表页要频繁按热度排序、详情页要展示"已报 X 人"，每次 `count(*)` 代价太高。它的正确性由 Redis 分布式锁保证——这正好是 M2 防超员压测要验证的东西：**锁失效会导致这个字段和实际报名记录不一致**，压测报告里应当显式对比两者。

索引：`idx_status_time (status, start_time)` 支撑活动流分页；`idx_organizer (organizer_id)` 支撑"我发布的"。

### `activity_tag` 活动标签

`activity_id` + `tag_name`，联合唯一索引。与用户标签同名匹配，是匹配权重的输入之一。

### `activity_image` 活动图片

`activity_id` + `image_url` + `sort`。单独建表而不用逗号分隔字符串：图片要过审核，分隔字符串无法对单张图做状态标记。

### `activity_signup` 报名记录

| 字段 | 类型 | 说明 |
|---|---|---|
| activity_id | bigint | |
| user_id | bigint | |
| status | varchar(16) | SIGNED 已报名 / CANCELED 已取消 / ATTENDED 已到场 / ABSENT 缺席 |
| remark | varchar(200) | 报名留言 |

联合唯一索引 `(activity_id, user_id)`，配合软状态（取消只是改 status 而不是删记录）。这条唯一索引是防超员的最后一道防线：即便应用层锁失效，数据库也不会出现同一个人报两次名。压测时"报名人数超过上限"和"同一个人重复报名"应当是两个分开统计的指标。

## 三、搭子域

### `buddy_request` 搭子需求

`user_id`、`title`、`description`、`category`、`lng`、`lat`、`time_range`（varchar，自由文本，如"周末下午"）、`status`（OPEN/CLOSED）。

搭子需求**没有人数上限，也没有截止时间**，这是它和活动最本质的区别。它只有两个终态：用户自己关闭，或者匹配成功自行联系。

### `buddy_tag` 搭子标签

`request_id` + `tag_name`，联合唯一索引。

## 四、通信域

### `chat_group` 群组

`activity_id`（可为空，预留非活动群）、`name`、`member_count`。活动创建时同步建群，见决策文件第五节。

### `chat_group_member` 群成员

`group_id` + `user_id` + `role`（OWNER/MEMBER）+ `joined_at`，联合唯一索引 `(group_id, user_id)`。报名成功即写入，退报名时软删除。

### `message` 消息

| 字段 | 类型 | 说明 |
|---|---|---|
| group_id | bigint | 群聊时非空，单聊时为空 |
| sender_id | bigint | |
| receiver_id | bigint | 单聊时非空，群聊时为空 |
| msg_type | varchar(16) | TEXT/IMAGE/SYSTEM |
| content | varchar(2000) | |
| read_status | tinyint | 0 未读 / 1 已读 |

索引：`idx_group_time (group_id, created_at)`、`idx_receiver_time (receiver_id, created_at)`。已读回执只更新单聊和"最后一条群消息"的读状态，不逐条记录每人已读到哪条——逐条记录会让消息表膨胀出一个数量级，而毕设场景里"未读总数"已经够用。

## 五、运营域

### `credit_log` 信用分流水

`user_id`、`change_value`、`reason`、`related_id`（关联活动或举报）、`operator_id`（管理端调整时非空）、`balance_after`。只追加不修改，是扣分申诉和管理端审计的依据。

### `report` 举报

`reporter_id`、`target_type`（ACTIVITY/USER/MESSAGE）、`target_id`、`reason`、`evidence`（图片 URL，逗号分隔）、`status`（PENDING/APPROVED/REJECTED）、`handler_id`、`handle_result`。

## 六、Redis 键规划

| 键 | 类型 | 用途 |
|---|---|---|
| `geo:activity` | GEO | 活动坐标索引，就近筛选 |
| `geo:buddy` | GEO | 搭子需求坐标索引 |
| `lock:signup:{activityId}` | String | 报名分布式锁，M2 防超员 |
| `sms:code:{phone}` | String | 验证码，TTL 300 秒 |
| `jwt:blacklist:{jti}` | String | 登出与封禁 |
| `activity:{id}:participants` | String | 报名计数缓存 |

Redis 只存索引、锁和短期状态，不存业务事实。任何键失效都不能造成数据丢失，只能造成性能下降或需要重建索引。
