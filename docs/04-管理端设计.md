# 管理端设计（M6）

本文是 M6 的唯一依据，`03-接口契约.md` 第七节那张七行的表在这里展开成可实现的契约；两处有冲突时以本文为准，TE 确认后我把 03 同步掉。验收标准是根 README 里那句"审核、封禁、看板可用"。

## 一、动工前必须先承认的三个缺口

写页面之前先把家底盘了一遍，管理端不是"在已有数据上做展示"，有三个缺口横在前面，每一个都牵连用户端：

1. **系统里没有任何东西能产生举报。** `report` 表在库里、契约第七节有 `GET /admin/report`，但用户端没有举报入口，`/api/report` 也不存在于契约——这张表从 M0 到 M5 是一张死表。管理端的"审核"如果只审活动，举报处理就成了无源之水。
2. **`user` 表没有角色字段。** 决策第二节写了"管理端复用同一套鉴权，额外加权限码校验"，但表里没有 `role`，JWT 里也没有 `role` claim，现在谁都分不出谁是管理员。
3. **`activity` 没有审核状态。** 契约第七节写了 `GET /admin/activity/pending`（待审核）+ approve/reject，字面是"先审后发"；但 M5 的用户端发布即 `OPEN` 立刻进活动流，表里也没有审核字段，两条路对不上。

## 二、三个决策（含推荐与理由，待 TE 拍板）

**决策 1：管理端身份 —— `user` 加 `role tinyint`（0 用户 / 1 管理员），JWT 签发时带 `role` claim。** 不建独立的 `admin_user` 表：毕设场景里管理员就是预置的一个手机号，独立账号表意味着第二套登录、第二次会话管理，收益为零。管理员复用 `/api/auth/login/password` 登录，`/admin/**` 由拦截器校验 `role` claim，非管理员返回 `403`。种子数据预置 `13900000001 / 123456`（昵称"管理员"）。

**决策 2：活动审核走"先发后审"，不走契约字面的"先审后发"。** 这一条改契约原文，需要 TE 像 M5 决策五那样确认。理由有三：信用分规则表里本来就写着"发布违规活动 −30（**管理端判定**）"——这句话只有在先发后审的语义下才成立，先审后发的活动根本发不出去，谈不上违规；先审后发要动 M2/M5 已验收的用户端行为（发布后立即可见），还得迁移存量数据；社区类产品先发后审也是常态，答辩时更好讲。落地形态：`activity` 加 `admin_status tinyint`（0 正常 / 1 下架），管理端可对任何状态的活动执行下架与恢复，活动流查询一律加 `admin_status = 0`。**刻意不用往 `status` 状态机里塞一个"已下架"值**——那个字段是用户侧行为（OPEN/FULL/ONGOING/FINISHED/CANCELLED），管理侧干预混进去之后，"ONGOING 但被下架"就没法表达了，两个维度分开各自干净。

**决策 3：M6 连带补用户端举报入口。** 契约加 `POST /api/report`（reporter 从令牌取，入参 targetType/targetId/reason/evidence?），M5 限定两个入口：活动详情页（举报活动）与他人主页（举报用户），`MESSAGE` 类型在表结构里保留、入口不做——聊天长按菜单牵扯手势交互，不值得在这轮做。mobile 侧改动是详情页和主页各加一个"举报"动作 + 一个提交弹层，走真实数据源，mock 同步实现。

## 三、封禁与信用分调整的落地语义

**封禁要"立即生效"，但不需要逐个拉黑令牌。** 现有机制是按 `jti` 拉黑（`jwt:blacklist:{jti}`），封禁时把该用户所有在途 token 找出来逐个拉黑做不到——登录时并没有登记"这个用户有哪些 jti"。改用一个按人维度的键：封禁时 `SET ban:user:{userId} 1 EX 7200`（TTL 等于 access token 的有效期上限，过期自动解除，不必依赖解封动作），`AuthInterceptor` 在现有黑名单检查之后多查这一个键，命中返回 `1002`（账号已被封禁，契约里已有这个码）。解封 `DEL` 该键。封禁动作本身同时把 `user.status` 置 1 落库——Redis 键只是即时生效的手段，底账在 MySQL，与"Redis 只存短期状态"的既定原则一致。

**封禁的连带行为刻意收窄：只拦新动作，不清洗存量。** 被封用户发起的 `OPEN` 活动不下架、已入群不踢出——下架和踢人都是管理员的显式动作，系统不替他做决定；被拦截的是登录、发布、报名、发言（拦截器统一在 `ban:user:*` 这一层挡住）。

**信用分调整复用既有流水。** `POST /admin/user/{id}/credit` 走 `CreditService`，`credit_log` 的 `operator_id` 记管理员 id、`balance_after` 记调整后余额——这张表从 M0 设计时就为审计留好了位，M6 只是第一个真正写入 `operator_id` 的调用方。调整后若分数低于 60，"禁止发布活动"的既有规则自然生效，不需要管理端额外做任何事。

## 四、接口清单

管理端统一前缀 `/admin/**`，拦截器要求 `role=1`，返回信封与错误码契约与用户端完全一致。4xxx 段位**本轮不用**——权限不足就是 `403`，资源不存在就是 `1004`，不新设码。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/dashboard` | 看板聚合，一次返回全部口径，见第六节 |
| GET | `/admin/activity` | 活动全量列表，参数 status/keyword/page/size |
| POST | `/admin/activity/{id}/takedown` | 下架，入参 reason |
| POST | `/admin/activity/{id}/restore` | 恢复展示 |
| GET | `/admin/report` | 举报列表，参数 status/page/size，默认 PENDING 在前 |
| POST | `/admin/report/{id}/handle` | 处理，入参 approved/handleResult |
| GET | `/admin/user` | 用户列表，参数 keyword（手机号/昵称）/page/size |
| GET | `/admin/user/{id}` | 用户详情，含信用分流水与举报历史 |
| POST | `/admin/user/{id}/ban` | 封禁，入参 reason |
| POST | `/admin/user/{id}/unban` | 解封 |
| POST | `/admin/user/{id}/credit` | 调整信用分，入参 changeValue/reason |

用户端连带新增一个接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/report` | 提交举报，入参 targetType（ACTIVITY/USER）/targetId/reason/evidence? |

举报处理的连带语义定死：**判成立 = 目标处置 + 举报人闭环**。活动被判成立 → 活动下架 + 组织者 −30；用户被判成立 → 被举报人 −20；判驳回 → 双方分数都不动。`handle_result` 写明处置内容，管理端列表里能看到处理人与结论，这条流水就是申诉依据。

## 五、库表变更

| 表 | 变更 | 理由 |
|---|---|---|
| `user` | 加 `role tinyint NOT NULL DEFAULT 0` | 决策 1 |
| `activity` | 加 `admin_status tinyint NOT NULL DEFAULT 0`，索引 `idx_admin_status` | 决策 2 |
| `report` | 无变更，补 `Report` 实体与 Mapper（表在 M0 就建好了） | 决策 3 |
| Redis | 新增 `ban:user:{userId}`，TTL 7200；键规划表同步 | 第三节 |

迁移脚本按既有习惯写在 `schema.sql` 之后的增量段落里，存量数据全部走默认值，不需要刷数。

## 六、看板的数据口径

契约第七节写的"活跃度、匹配量、地域分布"太粗，口径不定就是各说各话。这里定死，全部能在现有表上直接算出来，**不新增埋点**：

| 卡片/图 | 口径 | 数据来源 |
|---|---|---|
| 核心数字卡 | 用户总数、活动总数、当前 OPEN、待处理举报 | 四张表 count |
| 近 7 天趋势 | 每日新增：活动数 / 报名数 / 消息数，三条线 | 三张表各按 `created_at` 分组 |
| 活动分类分布 | 按 `category` 聚合的活动数 | `activity` group by |
| 用户地域分布 | 按 `last_lng/last_lat` 落到预设城市围栏（复用 M5 的地标表思路，就近归类） | `user` 全量 |

两处妥协说明：匹配量不进看板——匹配是即时计算，没有落任何调用记录，为了一个数字埋点不值得；"地域分布"没有城市字段可用，地址是自由文本，所以用坐标就近归到预设围栏，和 M5 活动发布的"预设地标"是同一套思路，口径诚实且可复现。

## 七、前端工程与页面清单

选型按根 README 已定的 Vue3 + Element Plus + ECharts，补齐实现层：Vite 构建、Pinia 管登录态、vue-router 做路由守卫（未登录跳登录页、`role≠1` 拒进）、axios 拦截器统一处理 `401`（跳登录）与 `403`（提示无权限）。本机资源紧张，Element Plus 全量引入的打包体积在管理端可接受，不做按需配置优化。

| 页面 | 内容 |
|---|---|
| 登录 | 手机号 + 密码，复用 `/api/auth/login/password` |
| 看板 | 四张数字卡 + 7 天趋势折线 + 两个分布图 |
| 活动管理 | 全状态列表、关键词搜索、详情、下架/恢复（下架必须填 reason） |
| 举报处理 | 列表（PENDING 置顶）、证据查看、判成立/驳回并写 handleResult |
| 用户管理 | 搜索、详情（信用分流水 + 举报历史）、封禁/解封、调分 |

## 八、M6 验收标准

沿用"每个里程碑都有硬验收"的规矩，四条全过才算 M6 收口：

1. 管理员登录后四类页面可用；非管理员令牌访问 `/admin/**` 返回 `403`，未登录返回 `401`。
2. 用户端提交一条举报 → 管理端列表出现 → 判成立 → 被举报方信用分流水出现对应记录（−20 或下架 + 组织者 −30），管理端列表状态变 APPROVED。
3. 封禁一个用户：该用户在 Flutter 侧操作立刻返回 `1002` 并被踢回登录页；解封后恢复。
4. 下架一个活动：Flutter 活动流与搜索不再出现它，详情直达返回 `1004`；恢复后重新可见。
