# 技术决策与业务规则

本文件记录项目在开工前必须拍板的事项，是后续一切代码的唯一依据。说明书里没写、而实现又必须知道的东西，都在这里定死。TE 在 2026-10-11 授权按推荐方案执行；其中决策五改动了说明书原文，已在该节标注并获 TE 确认。第六节在 M0 定下，第七节是 M3 补的匹配算式，第八节是 M5 补的前端选型——各节标题后括注了补定时机。

## 一、仓库结构：单仓库多模块

采用单仓库多模块，而不是三个独立仓库。理由有三：毕设只有一个交付物，导师检查时一个仓库就能看全；跨仓库必然出现版本对不上（前端调的接口和后端实际实现的接口不是同一版）；接口契约、数据库设计、实验脚本这些公共资产没有第三个地方可放。

```
meetbuddy/
├─ docs/      文档：决策、库表、接口契约、验收标准 —— 唯一依据
├─ server/    Spring Boot 3 + Java 21，后端主工程
├─ mobile/    Flutter，用户端 App
└─ admin/     Vue3 + Element Plus，管理端 Web
```

每个模块自带 README，写清启动方式和依赖版本。`docs/` 下的文档是全项目共享的，不属于任何单个模块。

## 二、登录：账号密码 + 验证码双通道

说明书只写了手机验证码登录，但验证码在 Flutter 浏览器预览阶段是硬伤——`flutter run -d edge` 跑在桌面浏览器里，没有真机收短信，每登录一次都要去 Redis 里翻验证码，联调效率极低。因此做双通道：账号密码通道给开发和演示用，验证码通道保留给答辩和真实流程。

- **密码**：BCrypt 存哈希，不明文、不 MD5。
- **验证码**：Redis 存，`TTL 5 分钟`，同一手机号 60 秒内只能发一次。开发期支持固定验证码 `123456`，开关是 `meetbuddy.dev.fixed-code-enabled`：**`application.yml` 里默认 `false`（生产语义），只有 `dev` profile 通过 `application-dev.yml` 覆盖为 `true`**。所以本地开发必须带 profile 启动——`server/run-local.sh` 默认就是 `dev`，手动起则要加 `--spring.profiles.active=dev`。不带 profile 时验证码是真随机且会真实下发，这条隔离是 M4 开工前补上的。
- **令牌**：JWT，Access Token 2 小时，Refresh Token 7 天。封禁和登出走 Redis 黑名单——JWT 是无状态的，但没有黑名单就无法立刻踢掉被封禁的用户，这对有审核功能的应用是必需的。
- **管理端**：复用同一套鉴权，额外加权限码校验。

## 三、前端启动时机：契约定完即并行

不等后端接口联调完再起 Flutter。接口契约（见 `03-接口契约.md`）定稿后，Flutter 侧用 mock 数据源开发，真实接口就绪时只替换数据源层，UI 代码不动。这样两条线可以并行，也避免"前端写完发现字段名不对"的返工。

mock 与真实数据源统一走同一个 repository 接口，切换靠一个编译期开关，不允许在业务代码里写 `if (isMock)`。

## 四、信用分规则

信用分是匹配权重的组成部分（占 10%），也用于风险管控。区间 `[0, 100]`，新用户初始 **100**。

| 行为 | 变动 | 说明 |
|---|---|---|
| 被组织者确认到场 | +3 | 活动结束后由组织者批量确认 |
| 获得他人好评 | +1 | 单场活动对同一人只计一次 |
| 报名后未到场 | −10 | 组织者标记缺席 |
| 开始前 2 小时内取消报名 | −3 | 临时放鸽子 |
| 开始前 2 小时外取消报名 | −1 | 提前说明，轻微扣分 |
| 举报被审核成立 | −20 | 管理端判定 |
| 发布违规活动 | −30 | 管理端判定 |

分数下限为 0。**低于 60 分禁止发布活动**，仍可报名。所有变动写入 `credit_log` 流水表，管理端可查，用户端可看自己的变动记录——没有流水，扣分就无法申诉，审核功能也就失去了意义。

## 五、活动状态机与建群时机（改动了说明书，TE 已确认）

说明书第 2 节写的是"满员自动建群"。**这里改为：活动创建时即建群，报名成功即入群。**

TE 于 2026-10-11 确认采纳这一改动，说明书正文不再同步修改，以本节为准。

理由是组局场景本身需要出发前协调——拼车集合点在哪、剧本杀选哪个本、谁带装备。如果满员才建群，前十九个人在整个报名期间没有任何沟通渠道，这个功能实际上就没用了。技术上，"满员瞬间建群并拉二十人"还制造了一个高并发写入点，与 M2 的防超员压测目标互相干扰。

于是"满员"降级为一个状态标记，只负责两件事：关闭报名入口、触发全员通知。

状态流转如下：

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `OPEN` | 报名中 | 活动发布 |
| `FULL` | 已满 | 报名人数达到 `max_participants` |
| `ONGOING` | 进行中 | 到达 `start_time`（定时任务推进） |
| `FINISHED` | 已结束 | 到达 `end_time`（定时任务推进） |
| `CANCELLED` | 已取消 | 组织者主动取消 |

`FULL` 状态下有人取消报名则退回 `OPEN`；`ONGOING` 之后不再接受报名变动。组织者取消活动时，群不解散，改为只读并推送通知。

定时任务用 Spring `@Scheduled` 每 5 分钟扫一次待推进的活动，不做分布式调度——单机演示环境够用，引入 XXL-Job 之类的调度中心对毕设是负收益。

## 六、目录与命名约定

- 接口前缀：用户端 `/api/**`，管理端 `/admin/**`，WebSocket `/ws`。
- 后端分层沿用 campus-market 的习惯：`controller` → `service` → `mapper`，实体放 `entity`，出参放 `vo`，入参放 `dto`。
- 时间字段一律 `LocalDateTime`，数据库用 `datetime`，不用时间戳——毕设演示时直接看数据库更直观。
- 金额类字段在本项目不存在（活动为免费组局），如后续加入，一律用 `BigDecimal`，禁止 `double`。

## 七、匹配评分公式（M3 补定）

契约第五节只定了权重（距离 0.4、标签 0.3、时间 0.2、信用 0.1），没定每一项怎么算。这里补死，四个分量统一归一化到 `[0,1]` 再加权求和，总分也是 `[0,1]`。

| 分量 | 权重 | 计算方式 |
|---|---|---|
| 距离 | 0.4 | `1 - 距离 / 搜索半径`，超出半径的候选根本不会进入候选集，所以这一项天然落在 `[0,1]` |
| 标签重合 | 0.3 | `交集大小 / min(双方标签数)`，用重叠系数而不是 Jaccard——标签多的用户不该因为分母大而被系统性压低 |
| 时间匹配 | 0.2 | 按需求发布者的最近活跃时间衰减：24 小时内 1.0，24 小时~7 天线性降到 0.3，更早 0.1 |
| 信用分 | 0.1 | `credit_score / 100` |

**"时间匹配"这一项需要说明。** 用户表里没有"空闲时间段"这样的字段，搭子需求的 `time_range` 又是自由文本，两者无法做真正的时段求交。所以这里退一步，用**活跃新鲜度**作为时间维度的代理：一个三天没上线的搭子，即使距离再近，联系上去大概率也约不成。这是个妥协，但比让 0.2 的权重恒定为一个常数更有区分度。

候选集的来源顺序是：**先 GEO 圈人，再算分**。Redis GEO 只负责把半径外的候选一次性过滤掉，剩下的通常只有几十个，加权计算在内存里做即可——不要反过来先把全表拉出来再逐条算距离。

## 八、前端技术选型（M5 补定）

`mobile/README.md` 里"状态管理待定"这一条，在 M5 开工时补齐。硬约束还是那条——本机磁盘和内存紧张，所以每个选型都要求是纯 Dart 包、或者干脆不引。

| 项 | 选型 | 为什么不是别的 |
|---|---|---|
| 状态管理 | Provider + ChangeNotifier | Riverpod / Bloc 都要额外的概念与样板代码；本项目只有登录态、活动流、聊天三块共享状态，够用且零代码生成 |
| 网络层 | `http` + 手写 repository | dio 的拦截器链、重试、转换器对本项目是过剩能力；统一信封与 401 处理在 `ApiClient` 里几十行就够 |
| 实时通信 | `web_socket_channel` | Web 上 `dart:io` 的 `WebSocket` 不可用，必须用它（内部按平台分派实现） |
| 本地存储 | `shared_preferences` | 只存两个令牌和一份用户缓存；Web 落 localStorage，真机落沙盒文件，一套代码两边跑 |
| 路由 | Navigator 1.0 直接 `push` | 页面不到十个、没有深链接与路由守卫需求，引 `go_router` 只多一层配置 |
| 地图选点 | 不做，改地标下拉 | 地图 SDK 依赖原生能力，与"先浏览器预览"冲突；用预设地标提供真实经纬度，GEO 链路仍是真跑 |

### mock 与真实数据源的切换

第三节已经定了"同一个 repository 接口、编译期开关、不允许 `if (isMock)`"。M5 的落地形态：

```
mobile/lib/
├─ config/env.dart          编译期常量：USE_MOCK / API_BASE / WS_BASE
├─ app_scope.dart           组合根，全项目唯一读 Env.useMock 的地方
├─ repository/
│  ├─ *_repository.dart     抽象接口（auth / user / activity / chat / chat_socket）
│  ├─ real/                 走 HTTP 与 WebSocket
│  └─ mock/                 内存假数据；MockStore 单例，保证页面之间看到同一份数据
├─ model/                   与 docs/03 的响应体一一对应
├─ state/                   ChangeNotifier：SessionState / ActivityState / ChatState
├─ page/                    页面
└─ widget/                  复用组件
```

切换靠 `--dart-define`，不改代码：

```bash
flutter run -d edge                                     # 连真实后端（默认）
flutter run -d edge --dart-define=USE_MOCK=true          # 纯前端假数据，后端可以不开
flutter run -d edge --dart-define=API_BASE=http://192.168.1.5:8099
```

`USE_MOCK` 用 `bool.fromEnvironment` 取，编译期定死，release 包里不残留 mock 分支。

**mock 必须与后端逐条对齐的六件事**（不对齐的话，切数据源就得回头改页面）：满员报名返 `2001`、重复报名返 `2002`、`lng/lat/radius` 三个都传才做半径筛选、创建活动即建群、取消活动后群转只读并落一条 `SYSTEM` 消息、群聊未读用"每人每群一个游标"而不是 per-message 已读位。

### 状态与生命周期约定（M5 实测后补定）

StatefulWidget 里**不允许在 `dispose()` 中用 `context`**。卸载顺序是 `Element.unmount()` 先把 `_widget`、`_inheritedElements` 置空并把生命周期改成 `defunct`，之后才调 `state.dispose()`；此时任何祖先查找（`context.read` / `Theme.of` / `Navigator.of` …）都作用在已失效的 Element 上。debug 下会给出明确提示，release 下只会抛 `Null check operator used on a null value`，且堆栈是压缩后的 `main.dart.js` 帧，几乎无法反查。

规矩两条：

1. 需要在 `dispose()` 里"离开时通知谁"，就在 `initState` 里先把引用拿住（`late final ChatState _chat = context.read<ChatState>()`），`dispose()` 只碰这个引用。之所以能在 `initState` 里 `read`，是因为它不注册依赖、只取一次值。
2. `initState` 里的 `addPostFrameCallback` 回调，第一行一律 `if (!mounted) return;`——回调可能在页面已被移除之后才执行。

## 九、交互手感与动效（M5 后补定）

起因是 TE 的一句反馈：「交互太僵硬了，没有呼吸感」。**先给判断：僵硬不是"动画太少"造成的，加时长只会更钝。**真因是三条可量化的事实——77 处点击目标里只有一部分给了按压反馈（筛选 chip、统计格子完全零反馈）；骨架屏是静态灰块摆在那儿，没有在"等"的语义；页面入场动画总时长偏长（360ms 延迟 + 550ms 上浮），每次 push 都觉得卡半拍。所以下面每一条都是按证据改的，不是按感觉调参。

### 三种点击反馈，按语义选，不许混用

| 组件 | 语义 | 行为 | 用在哪 |
|---|---|---|---|
| `PressableScale` | 常规可点区域 | 按下 110ms 缩到 `scale`（默认 0.96）+ 压暗到 0.94；抬起 220ms 用 `easeOutBack` 弹回 | 卡片、按钮、chip、统计格 |
| `BouncyTap` | 状态翻转型图标 | 1 → 1.18 → 0.94 → 1 的 `TweenSequence`，260ms | 收藏、点赞这类"点了会变"的图标 |
| 无包裹 | 纯展示 | — | 无点击行为的一切 |

`PressableScale` 是**快压慢回**（110 / 220ms）。反过来（慢压快回）会让按下像陷进泥里。`easeOutBack` 在回弹末端有轻微过冲，这是"呼吸感"的主要来源；换 `easeOut` 立刻变木。

`_set(bool down)` 里必须先判等再 `setState`——`onTapDown` 在按住期间可能每帧触发，不判等就是每帧重建整棵子树，手感没变好反而掉帧。

用 `PressableScale` 包 `IconButton(onPressed: null)` 是**刻意**的：`onPressed: null` 关掉 IconButton 自己的水波纹，把点击语义交给外层，避免两套反馈叠加。

### 骨架屏是扫光，不是呼吸

`SkeletonBox` 用一条 `LinearGradient` 高光带从 -1 走到 2（1250ms 循环），而不是整体明暗呼吸。明暗呼吸在浅色底上几乎看不出，且会让整块区域一起变亮变暗，像页面在闪；扫光只有高光带在动，方向明确，读起来是"正在加载"而不是"页面在闪"。`SkeletonList` 里每块再包一层 `_Shimmer`，挂载时 260ms 淡入——否则骨架替换成真数据是硬切。

### 入场动画：总时长压到 528ms 以内

`StaggeredIn` 的规则是**每项延迟 38ms、最多计 6 项**，即最晚一项在 228ms 起步，配上浮时长 300ms，全树 528ms 内收完。之前是 55ms × 上限 10 项，最晚 360ms 起步 + 550ms 上浮 = 910ms——列表越长越像卡住。

上浮距离同时从 14 收到 10。距离和时长是乘积关系，一起收才有"轻"的感觉；只收时长、不动距离，会看着像"快速滑了一大段"，更显黏。

### 覆盖范围

新写页面时，**任何可点的东西都要落到上面表格的某一档**。判断法：把页面上所有 `GestureDetector` / `InkWell` / `onTap` 数一遍，逐个问"按下去有没有视觉变化"，答不上来就补 `PressableScale`。M5 第 2 批结束时这条已在 profile / user-profile / follow-list / notification / activity-feed / detail 六个页面覆盖到位。

### 主/次按钮：共用一套"压下去"，但配色分两路

`PrimaryButton` 与 `GhostButton` 都不套 `PressableScale`，共用 `_BouncyButtonBody`。理由是这两颗按钮**宽近满屏、高 54**，整块按 `PressableScale` 缩放会让左右边缘来回缩进，看着像条橡皮筋；而"按下去了"的视觉重量应该落在手指底下、由内往外传，不是整个矩形一起动。所以 `_BouncyButtonBody` 做三件事：缩放 0.965（比整卡略深，胶囊横向长）、底色与边框 90ms 压下 / 200ms 回弹、**按下时投影收掉**（只缩不缩影，按钮会像浮在原地缩小）。

配色分两路是因为两者"按下"的可用信号不同：黑底按钮靠**变亮**（`#171A1D` → `#3A4249`），白底按钮不能靠变暗——白再暗也是白，改成填一层极浅的品牌蓝并把边框转蓝，确认感来自色相而不是亮度。

`GhostButton` 因此留了四个配色覆盖口（`background` / `borderColor` / `textColor` / `iconColor`）加一个 `child` 槽。它们的存在只为一种情况：**非禁用、非正常的中间态**（如倒计时）。这类状态不该被硬编码进一个被 7 处复用的通用组件。

### 中间态不是禁用态

「获取验证码」有三种状态，语义上不是"可用/不可用"两档：

| 状态 | 画法 | 为什么 |
|---|---|---|
| 可点 | 白底描边 + 纸飞机图标 | 图标说明"这一下是发出去" |
| 发送中 | 转圈 | 缺这一档，弱网下用户会连点，撞上后端频控</br>报一串"操作太频繁" |
| 倒计时 | **浅蓝底 + 蓝字 + 进度环**，永远不是灰 | 灰按钮读起来是"这功能坏了"；而倒计时是"已经发出去了，在等" |

倒计时同时用**数字和环形**表达剩余时间：数字精确但需要读，环形可以余光扫。宽度**固定 116**——三档文案字数不同，不固定的话按钮随秒数变宽窄，会把左边正在输入的手机号横移，这是最烦人的一类抖动。

由此推出一条通用规矩：**`onPressed: null` 表达的是"这功能现在不可用"，不表达"正在处理"。**后者要用自己的配色与动效，否则会把"进行中"误读成"坏了"。

### Tab 切换与底部导航：指示器要"滑过去"，不要"各自变色"

两处的选中指示都用**一个会滑动的胶囊**，而不是选中项原地变色。

- **底部导航**（`_NavDock`）：滑块用 `AnimatedAlign` 走位置、`FractionallySizedBox(1/3)` 定宽，`Curves.easeOutBack` 让它"撞"进目标位再回弹。不需要测量宽度，天然跟着等分伸缩。滑块在底层、`IgnorePointer` 包住——否则它吃掉点击，下面的 item 永远点不到。图标另叠 `AnimatedScale` 1.08，因为 9.5px 的文字变色在一眼扫过时看不到。
- **TabBar**（`_PillIndicator`）：只负责"把胶囊画在给定矩形里"，位置与跨 tab 插值全交给 TabBar（它按 `indicatorSize: label` 算好宽度、通过 `offset` 传入）。**自己算宽度会让两端文案长度不同时（'关注'/'粉丝' 与 '我发起的'/'我报名的'）胶囊跟着抖。** 形状按"高度一半"当半径，不用固定 `circular(999)`——后者在指示器被压窄时会退化成两个圆加一条线。跨 tab 用 `TabIndicatorAnimation.elastic`。

**切换必须可见**：`TabBarView` 的 `physics` 在**所有含滚动列表的 tab 上都设成 `NeverScrollableScrollPhysics`**。横滑手势会和列表纵滑抢事件，斜着滑一下列表就翻页了。手势关掉后，点击 tab 的内容过渡由 `_TabFade`（挂 `TabController.animation`，淡入 + 6px 上浮）补上。

内容加载的骨架 → 真数据也是**淡入不是硬切**：`AnimatedSwitcher` 260ms，旧内容 140ms 先走、新的不等——叠着走比排队走快，且不留空白帧。

### 封面上的日期徽标：两条分支必须都画

`ActivityCover` 走两条分支——有 `coverUrl` 用真图，否则用 `MapScene` 插画兜底。日期徽标原先**只画在插画分支上**，于是"用自己拍的封面"的活动反而没有时间信息，而这恰好是最需要一眼看到时间的场景（feed 卡片就是靠这张图决定点不点进去）。修法是两条分支都画，位置一致（左上 12/12）。

真图分支额外压一层**底部渐变遮罩**：照片左上角不保证是浅色，胶囊自身的投影糊在复杂纹理里会失去边界。

时间文案的口径与小程序 `utils/format.js` 的 `timeBadge` **逐字对齐**（`今天 19:30` / `明天 09:00` / `10月17日 14:00`），改一处必须同步另一处。另外判定"是不是今天"用独立函数而不是 `text.startsWith('今天')`——字符串判定把"文案生成"和"配色决策"绑在一起，将来把文案改成"今日 14:30"或在前面加图标，这个 `startsWith` 会静默失效：不报错，只是今天的活动不再显示成蓝色，没人会注意到。

### 两条容易踩的插值坑

**`BoxDecoration.lerp` 在 `null` 与 `List<BoxShadow>` 之间不插值。** `AnimatedContainer` 里把 `boxShadow` 从一层阴影改成 `null`，过渡期间会在某一帧整个消失——看起来不是"按下去"，是"闪了一下"。要"让阴影消失"就给它一个**同色、零位移、零模糊**的阴影：视觉上等同没有，但插值能一路算过去、不跳变。

**浅色系的"更深一档"不能靠调透明度。** `color.withValues(alpha: 0.78)` 是在透明底上做合成，不是往白底混：`#E1F4FE`（浅蓝）乘 0.78 后合成值 `(232,246,254)` 比原色 `(225,244,254)` **更浅**，按下时底色等于消失。浅色要变深只能换色值（`#E1F4FE` → `#D3EDFC`），或者用 `Color.alphaBlend` 显式指定底色。

## 十、表单与按钮的质感（M5 后补定）

TE 追加要求「提升表单和按钮的质感」。先给判断：**质感的来源是分层，不是装饰。** 改动前所有表面都是平的——输入框是 `#F3F8FC` 填充 + `#E4EEF6` 边框（两个色只差 `0x0F`，等于没有边框）；按钮是纯色平涂；光标还是默认的 Material 蓝紫。所以这次加的不是阴影和圆角，而是**把每一层该做的事分开**：背景层、边框层、内容层、受光层。

### 输入框：`AppField`，不用裸 `TextField`

所有表单输入走 `widget/ui.dart` 的 `AppField`，**不要直接写 `TextField`**。

为什么必须包一层而不能只改 `inputDecorationTheme`：Flutter 的 `InputDecorator` 在 focus 变化时是**瞬时重建**的——border 与 fillColor 直接跳变，没有过渡。而"被点亮"的质感恰恰来自这个过程。theme 里改多少颜色都做不到，只有自己用 `AnimatedContainer` 画背景和边框才行。

`AppField` 的做法：把内部 `TextField` 剥到只剩文字（`border: InputBorder.none` + `filled: false` + `errorStyle` 压成零高），背景、边框、光晕、padding 全部由外层 `AnimatedContainer` 画，**内外 padding 只留一处**（外层的 `horizontal: 14`），否则会叠加成双倍内边距。

| 状态 | 填充 | 边框 | 光晕 |
|---|---|---|---|
| 常态 | `#F3F8FC` | `#DEEBF4` 1.5px | 无 |
| 聚焦 | 白 | `#38B2F2` 1.8px | 8px 蓝色 14% |
| 错误 | `#FEF4F6` | `#FF5B7A` 1.8px | 8px 玫红 16% |
| 禁用 | `#EDF1F5` | `#DCE5EC` | 无 |

四件事同步走 180ms `easeOut`。几个刻意的选择：

- **常态边框压深到 `#DEEBF4`**，不用主题里的 `#E4EEF6`。填充是 `#F3F8FC`，两者只差 `0x0F`，等于没有边框，输入框看起来是一坨平灰块。压深一档轮廓才立得住，又不会抢过聚焦态的蓝。
- **聚焦时填充褪成白**，不只是边框变色。边框变色在浅蓝渐变背景上会被背景吃掉，必须配一个 8px 的蓝色外圈光晕才看得见。
- **图标跟着 focus 变色**（`TweenAnimationBuilder<Color?>` 插值）。瞬时切换也能用，但插值让"聚焦"有了一个可感知的过程。
- **字段用 `hintText` 而不是 `labelText`**，这是刻意的。Flutter 的 floating label 会上浮到 border 的位置，而这个组件的 border 是自己画的（内部那层是 `InputBorder.none`）——label 上浮后会画在容器顶缘，跟自己的边框重叠甚至溢出。项目里的表单都只有三四个字段，不需要靠浮动标签省空间。
- **错误态用淡粉底 + 玫红边**，不用纯红 `#F44336`。这套设计的底色是天蓝，纯红在里面像贴上去的警示条。玫红与 `AppBrand.hot` 同色相，既看得见又不破坏色调。
- **错误文字渲染在输入框下方**（`_ErrorLine`），不让 `TextFormField` 内部显示——内部那行会被 `contentPadding` 与 `maxLines` 搅乱高度，且配色跟自绘边框不同源。错误状态从 `FormFieldState.hasError` 读，**不自己维护一份**（两份必然不一致）。

全局另配 `textSelectionTheme`：光标 `primaryDeep`、选区 20% 品牌蓝、选区手柄 `primary`。默认是 Material 的蓝紫，在一套天蓝设计里出现两秒紫光标是很损质感的细节。

### 按钮：渐变 + 受光边

`PrimaryButton` 与 `GhostButton` 共用 `_BouncyButtonBody`，材质由 `_ButtonFace` 定义——**常态与按下各一条竖向渐变**：

| | 常态 | 按下 |
|---|---|---|
| 深色胶囊 | `#2E353C` → `#14171A` | `#242A30` → `#0E1113` |
| 白胶囊 | `#FFFFFF` → `#F6FAFD` | `#F2F8FC` → `#E6F1F9` |

为什么要渐变：**纯色没有方向信息。** `#171A1D` 涂满一个胶囊，它是一块平面；从 `#2E353C` 渐到 `#14171A`，上亮下暗，它立刻有了受光面和厚度——这正是真实按钮与"设计稿截图"的差别。代价只有一次 `LinearGradient`。

明度差刻意压得很小（黑底 10 个色阶、白底 3 个色阶）：差大了会变成上个十年的"渐变按钮"，且小尺寸上出现色带。这一档是"看得出有层次、但说不出哪来的"程度。

深色按钮额外画一条 **1px 顶部受光边**（`#2E353C` 上方一条 16% 白的渐变线，两端渐隐）。没有它，渐变只是"上亮下暗的一块"；有了它，那条亮边就是"这个面的上缘被光照到了"，厚度才成立。用 `Stack` + `Positioned` 而不是 `border`——border 会画在四条边上，而受光只来自上方。白底按钮关掉它（白加白看不见，反而糊掉边框）。

**禁用态一律退回纯色**，不走渐变。渐变按钮置灰会有"灰得有层次"的怪感，禁用态就该是一块平的、明确没有质地的颜色。
