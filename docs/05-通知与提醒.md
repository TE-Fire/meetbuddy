# 通知与提醒

> 本文定"系统通知 + 活动开始前提醒"的规则，是代码实现的唯一依据。M7 落地。

## 一、要解决什么

私聊有 WebSocket 实时推送，但**非聊天类事件**（有人报名我的活动、活动被取消、活动即将开始）此前没有任何触达渠道——用户只能自己反复进页面看。补一套站内通知 + 定时提醒，把这些事件主动送到用户面前。

互评已砍掉：TE 2026-10-14 拍板该功能无用，全项目不再设计、不再预留。文档与代码中不出现互评相关内容。

## 二、通知事件清单

| type | 触发时机 | 接收人 | 内容 |
|---|---|---|---|
| `SIGNUP_NEW` | 有人报名我的活动 | 组织者 | 「昵称」报名了你的活动「标题」 |
| `ACTIVITY_CANCELLED` | 组织者取消活动 | 全部有效报名者 | 你报名的「标题」已被组织者取消 |
| `ACTIVITY_REMINDER` | 活动开始前 N 分钟（提醒） | 组织者 + 全部有效报名者 | 「标题」将在 N 分钟后开始 |
| `ACTIVITY_TAKEDOWN` | 管理端下架活动 | 活动组织者 | 你的活动「标题」已被管理员下架（附原因） |
| `REPORT_HANDLED` | 管理端处理举报 | 举报人 | 你举报的活动/用户已处理完成（附处理结果） |

几个口径：

- **报名通知的接收人天然不是操作者**：`doSignup` 已挡"组织者报名"，所以 SIGNUP_NEW 的接收人（组织者）不可能是刚操作的人。
- **取消通知不发组织者**：组织者是取消行为的发起者，且组织者本就不在报名列表里。
- **提醒只发一次**：靠 `activity.reminded` 置 1 防重，不依赖 Redis。
- **管理侧两条的挂点**：`takedown`（直接下架）和 `handleReport` 举报成立连坐的下架都发 `ACTIVITY_TAKEDOWN`；`handleReport` 不论成立与否都给举报人发 `REPORT_HANDLED`——驳回也要有回音，否则用户会以为举报石沉大海。`REPORT_HANDLED` 的 bizId 存的是被举报目标（可能是用户），前端不据此跳转。
- **封禁/解封不通知**：封禁时用户登录态已被即时拦截，发通知本人也看不到；解封通知价值有限，先不做，需要时在 `unban` 末尾加一行即可。

## 三、提醒的定时扫描

`@EnableScheduling` 已启用（M4 心跳巡检在用），直接加一个每分钟跑的 `ReminderJob`：

1. 查 `reminded=0 AND status IN (OPEN,FULL,ONGOING) AND start_time ∈ [now, now+提前量]` 的活动（limit 100）。
2. 收件人 = 组织者 + 该活动有效报名者；逐人落通知。
3. 置 `activity.reminded=1`。

提前量默认 **30 分钟**，配置项 `meetbuddy.notification.reminder-lead-minutes`。单机演示用一分钟一轮的 `fixedDelay` 足够，不上分布式调度。

## 四、存储与已读

新表 `notification`：`user_id / type / title / content / biz_id / read_status / created_at`。已读用 `read_status`（0/1）——一条通知一个接收人，和单聊消息一个路子，不需要群聊那种游标。

未读数 = `count(user_id=me AND read_status=0)`，与聊天未读**分开统计**（前端 tab 红点若要合并，在客户端相加）。

## 五、触达：落库 + 在线实时推

`notifyUser(s)` 落库后，若接收方当时在线（`ChatSessionRegistry` 有连接），经 WebSocket 补推一帧：

```json
{ "type": "notify", "notification": { "id": 1, "type": "ACTIVITY_REMINDER", "title": "...", "content": "...", "bizId": 41, "readStatus": 0, "createdAt": "..." } }
```

离线则只落库，靠未读红点 + 下次进通知页补看。`notify` 帧与聊天帧复用同一条 WS 连接，客户端 `socket.js` 多认一个 type 即可。

## 六、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/notification` | 我的通知分页，参数 page/size，按时间倒序 |
| GET | `/api/notification/unread` | 未读数 |
| POST | `/api/notification/{id}/read` | 标记单条已读 |
| POST | `/api/notification/read-all` | 全部已读 |

错误码占 **32xx** 段（`NotificationErrorCode`）。

## 七、前端（已实现）

- 「通知」页 `pages/notification/`：类型图标、未读点、相对时间、触底分页、点击标已读；活动四类（SIGNUP_NEW / ACTIVITY_CANCELLED / ACTIVITY_REMINDER / ACTIVITY_TAKEDOWN）按 bizId 跳详情，REPORT_HANDLED 不跳。
- 入口在消息页顶部（chat-list 的铃铛行），不是 tab bar——tab bar 三个位置对应发现/消息/我的既有结构，不新增第四项。
- tab bar 徽标 = 聊天未读 + 通知未读，`globalData.unreadChat` / `unreadNotif` 两份分别由两个页面维护，`refreshUnread` 取和。
- `socket.js` 已有帧分发，chat-list 与通知页都认 `notify` 帧：chat-list 只刷未读，通知页（在前台时）直接重载列表。
